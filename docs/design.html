Nightshift factory map

An interactive view of docs/design.md: what the factory is made of and how one request travels from a chat message to production. The design document is the source of truth; section numbers below point into it.

Tenant profile: Theme:

Two independent settings. The profile (solo or team) says who decides: in solo the factory merges and releases on the owner's button; in team it hands a ready PR to the team and stops at handed_off. The instance (personal or work) is a trust boundary: whose code, secrets and providers. A personal project is usually solo, an employer project team. The switch above changes the profile.

1. Components and the path of a request (design §3, §4, §7)

One docker compose up. Step through a request to light up the parts it uses; click a box for details.

2. Roles (design §6)

Three agents plus a nightly job. A role is a YAML config; everything else is Go code.

3. Quality loop before a human (design §8)

Cheap checks first. The owner sees a task only when every layer is green.

Gates: the repository's .nightshift/gates.yaml sets each check or layer to block, warn or off, optionally by paths or blast radius level. Without the file every check blocks. gitleaks, osv-scanner, the security rules, verify and CI cannot be lowered; weakening a gate is critical and needs the owner's Approve. nightshift check --plan shows what applies to a diff. An agent reads and changes the gates through the MCP door, and every change is a PR.

4. Review policy (design §11)

Blast radius is computed by code from paths, signals and tags. Agents can only raise it.

Mode ladder: all → blast_radius → off (team stops at blast_radius). An escape, revert or rollback moves a tenant one rung up at once; a clean window of 30 mature tasks and 14 days only proposes a step down, applied by the owner's button.

5. Memory (design §13)

No separate agent brain: each memory type maps to something that already exists. One retrieval interface: full text always; with an embedder configured, vector search fused by Reciprocal Rank Fusion. Off by default, on when the search eval shows a gain.

6. Connecting a project (design §17)

Discovery is plain code; the interview is one skill that any harness can run. Nothing about a project of another instance is read. A project customizes the factory only with files in its own repository: AGENTS.md, skills in .agents/skills/ or .nightshift/skills/, rule cards in .nightshift/standards/, its own packs in .nightshift/stacks/, the toolchain in mise.toml, and setup and verify in project.yaml.

7. Engineering disciplines (design §9, §12, §17)

A discipline is cards, the tools of stack packs and catalog skills. No new roles. Stack packs exist per language (go, python, ts, js, java-maven, java-gradle) and per technology (openapi, postgres, docker, web); discovery proposes them from their detect files. A language without a pack runs on the project's toolchain and verify; frameworks are skills selected by the project's dependencies, not packs. A project sets card params with a reason; load testing is the project's load capability.

8. Phases and status (design §22)

Each phase starts only when the previous Done criterion is met. The item list, the order inside the current phase and the blockers live in docs/plan.md and docs/status.md; make verify fails when the current phase or the item counts below differ from docs/plan.md.
