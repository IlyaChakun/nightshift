# Codebase intelligence and change impact analysis

Give Lead, Builder and Verifier a compact, evidence-backed map of the affected system before changing an existing codebase. Start with deterministic dependency queries and a conservative test plan; only invest in a persistent index when measured retrieval or impact-analysis failures justify it.

**Priority:** P1. **Status:** research proposal, not approved implementation.

## Problem

Harness search is effective for local edits but may miss callers, schema consumers, runtime configuration and cross-service contracts. Passing tests in one package does not establish that a change is safe elsewhere. An agent-generated architecture summary can also become stale or falsely authoritative.

## How it works

Generate a read-only change brief against an exact repository revision. Combine the diff, stack-native dependency information, interfaces and contracts, ADRs, ownership, relevant tests and previous findings. Distinguish observed edges from inferred edges and unknown runtime dependencies; cite paths and revisions, not unsupported claims.

A proposed brief contains the base/head revisions, changed symbols and contracts, affected consumers, invariants, risk hotspots, proposed checks, unknowns and evidence locations. Lead uses it to scope work, Builder to select implementation context, and Verifier independently checks whether the brief missed relevant consumers.

## Trade-offs

| Option | Benefit | Limitation |
| --- | --- | --- |
| Harness search and repository docs | Minimal infrastructure | Coverage varies by run |
| On-demand stack-native graph and diff analysis | Reproducible, cheap, revision-bound | Dynamic edges may be absent |
| Persistent symbol and dependency index | Reuse across many tasks | Invalidation, storage and language maintenance |
| Semantic retrieval or graph-based retrieval | Finds conceptual relationships | Probabilistic; cannot establish completeness |

Prefer on-demand analysis. For Go, investigate native package dependency queries first. For other stacks, use the existing build graph or manifest where available. Do not make a vector store or an additional service a prerequisite.

## Status

Partial foundation at the pinned base: package notes, repository search, stack packs, task dependencies and a merge train are documented. Automated revision-bound impact briefs are a candidate gap; a full code inventory is not performed.

## Proposal

Select one brownfield repository with representative tasks: internal API change, database migration, authentication fix, shared library change and configuration change. Freeze the inputs and independent acceptance scenarios.

1. Establish a harness-only baseline.
2. Add a small read-only impact brief generated by existing stack tools.
3. Compare affected-consumer recall, false positives, tests missed, context tokens, wall time and accepted outcomes.
4. Keep the brief advisory until evidence supports blocking use.

Unknown impact must fall back to the existing full mandatory checks. Cache by revision and tool/config version; discard stale results. Tenant isolation applies to all maps and source excerpts.

## Acceptance and stop conditions

- A planted cross-module breaking change is identified or explicitly classified as unknown.
- A changed base invalidates the prior brief; no stale brief authorizes a release.
- A missed dynamic dependency cannot narrow mandatory tests.
- On paired tasks, the new approach improves impact recall or accepted outcomes without unacceptable latency or cost.
- Stop if ordinary harness search plus better ADRs gives comparable results. Defer persistent indexing until measured scale warrants it.

## Decision brief — revision-bound impact analysis, 2026-11-26

**Decision:** test a stack-native, on-demand impact brief, first as an optional skill/tool in the existing worker. Keep harness search as the default and never narrow mandatory verification from an impact map. A persistent symbol index, GraphRAG and a new service need evidence beyond the initial pilot.

### Primary research and limits

Sources opened 2026-11-26; paper claims below are authors' results, not independent reproductions.

| Approach and source | Evidence and implications |
| --- | --- |
| [Go list](https://pkg.go.dev/cmd/go#hdr-List_packages_or_modules), [go/packages](https://pkg.go.dev/golang.org/x/tools/go/packages) | Native package information, test variants, source paths, imports and optional types/syntax. Build configuration matters. Start with the existing toolchain and no dependency; typed loading is a later refinement. |
| [Bazel query reference](https://bazel.build/query/language) | Reverse graph queries and conservative configuration approximations illustrate a portable method. Use native build graphs only where the repository already uses them; do not adopt Bazel. This replaces the earlier excerpt-only source status for the technique. |
| [Aider repository map](https://aider.chat/docs/repomap.html) | Compact symbol/signature map ranked over file relationships under a context budget. Good navigation precedent, not a proof of impact completeness or a measured Nightshift gain. |
| [Agentless, arXiv v2, 2024-10-29](https://arxiv.org/abs/2407.01489v2) | Structured localization, repair and validation achieved 96/300 resolved SWE-bench Lite tasks in the authors' setting. Historical models/benchmark and full pipeline confound the effect of localization alone. Use as rationale to compare a simple structured baseline, not to replace the harness. |
| [RepoCoder, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.151/) | Iterative similarity retrieval for repository-level code completion. Completion is not multi-file repair or release assurance; semantic retrieval is a candidate supplement when lexical search misses evidence, not an authoritative graph. |
| [Go RTA](https://pkg.go.dev/golang.org/x/tools/go/callgraph/rta) | Whole-program analysis can refine possible interface dispatch; the documented call graph excludes reflection-call edges. Do not imply a complete graph of dynamically loaded code or remote consumers. |
| [Ekstazi, ISSTA 2015](https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL15Ekstazi.pdf), abstract and page 1 | Authors report average 32% end-to-end test-time reduction across 615 revisions of 32 Java projects, using dynamic file dependencies. This is evidence for investigating regression selection under explicit assumptions, not evidence that Go import reachability safely replaces CI. |

### Reproducible feasibility check

**Executed 2026-11-26:** a disposable, dependency-free Go module with Go 1.23.2 linux/amd64, no model calls, no external network required. This is a mechanism check, not a run of Nightshift or its pinned toolchain.

Construct five packages in module `example.invalid/impact`: core exports Value returning 1; svc imports core; api imports svc; conditional contains a normal empty package file and a file with build tag special importing core; probe has an empty normal package file and an external test package importing core, asserting Value equals 1.

```bash
export GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local GOWORK=off
go list -deps -test -json ./... > default.json
go list -tags=special -deps -test -json ./... > special.json
```

Decode the concatenated JSON objects; reverse their Imports edges; traverse from core within the module namespace. The following are observed nodes (module prefix omitted), not estimates:

| Configuration | Reverse reachable nodes including seed |
| --- | --- |
| Default | api, core, svc, probe.test, probe_test [probe.test] |
| special | api, conditional, core, svc, probe.test, probe_test [probe.test] |

Changed core.Value to return 2 and executed `go test ./probe`: TestValue failed with "changed". Thus the external test consumer matters, and the default graph alone omits the special build consumer. Normalize synthetic test package identities to owning packages before presenting a test plan. The experiment does not establish behavior of other languages, module workspaces, generated code or real projects.

### Minimal design for the experiment

1. Run a bounded read-only extractor in the existing isolated job environment after checkout, using the project's native toolchain and approved build configurations. Resolve the repository identity and base/head revisions through the conductor. For planning without a diff, accept a seed set of paths/symbols explicitly marked provisional.
2. For Go, use the package graph from the two relevant trees, including test variants. Seed changed/added/deleted/renamed paths in their respective trees; take the union of reverse reachability. Record known configured build tags, GOOS/GOARCH, workspace/module and toolchain versions. Handle parser/build failure, missing generated code and unresolved imports as unknown, not empty.
3. Add contract hints from configured schema/API/migration files, manifests, routes, message topics and configuration references where available. Distinguish deterministic import edges, observed test or trace edges, owner-declared contracts, lexical candidates and model hypotheses. No inferred edge authorizes or excludes a check.
4. Emit a compact advisory artifact: revision pair, extractor/config identity, seeds, affected packages/consumers, edge provenance, candidate tests, known gaps, truncated/unknown flags and links to evidence. Rank context for the role under a bounded token budget; report overflow rather than silently dropping high-risk candidates.
5. Lead uses the provisional map for scope; Builder uses it to prioritize exploration and early tests; Verifier independently recomputes on the actual candidate and challenges omissions. After rebase, base change or different build inputs, invalidate/recompute. Do not use candidate-modified policy as the source of mandatory test scope.

Cache only if repeated graph generation is measured to be a bottleneck. Cache keys include tenant, repository identity, base/head, toolchain, extractor and build configuration; dirty trees need a content digest or no cache. Keep output job-scoped and sanitized; no hidden scenarios, secrets, unauthorized mirrors or cross-tenant code. Do not run a repository build script with control-plane privileges. Missing/unsupported analysis falls back to the unchanged harness workflow and all mandatory gates, not a permissive pass.

### Comparative experiment and decision criteria

| Arm | Context and execution |
| --- | --- |
| A | Existing harness navigation, docs and mandatory checks. |
| B | Same harness/model/tools/budget, plus the deterministic revision-bound brief. Mandatory checks remain identical. |
| C (only if needed) | B plus typed/symbol-level or semantic retrieval; compare only after failures in B identify a precise need. |

Use frozen, independently reviewed brownfield tasks spanning API change, database migration, auth, shared library, generated source, config and cross-service contract. Include at least one task with no real dependency impact to measure overreach. Pair the same starting revision and acceptance contract; separate environments, randomize order, avoid leaked answers. Initial calibration size is a budgeted design choice, not statistical proof. #342 governs experimental accounting; #345 governs economics.

Measure required-consumer recall (found independently adjudicated relevant consumers / all adjudicated relevant consumers), false-positive review burden, omitted known failing tests versus a full mandatory run, accepted objectives, attempts, operator minutes, total cost, time and map generation latency. An original fix's touched-file list is only a hint, not ground truth for all impacted consumers. Keep independent adjudication blind to arm where possible; retain ambiguous labels and failed runs.

Required tests: renamed/deleted package, build-tag-only edge, external test package, stale base after rebase, missing tool/import, dynamic config/remote consumer, truncated map, hostile instructions in source and denied cross-tenant access. Every mandatory check executes regardless of mapping success. A planted critical impact must be identified or explicitly escalated as unknown; a stale map never authorizes the next state. Unknowns and overbroad warnings are measured, not concealed as high recall.

**Go/no-go:** adopt B only if a paired pilot shows a credible improvement in accepted outcomes, missed critical consumers or human effort without worse safety/quality or unacceptable cost. If baseline is comparable, keep harness search and improve docs instead. Add C only when repeated localization failures are identifiable and a second experiment demonstrates marginal benefit. Test prioritization may run in shadow mode; replacing mandatory full CI is a separate risk decision, not part of this PR.
